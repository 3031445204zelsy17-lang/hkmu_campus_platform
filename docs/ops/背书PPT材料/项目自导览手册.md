# HKMU 校园平台 · 项目自导览手册

> **这份手册是什么**：让你（SYF）完全掌握自己项目的说明书——不看代码也能讲清「系统长什么样、东西放在哪、怎么发布、出事怎么救」。
> **怎么用**：按 0→5 讲顺序读，每讲末尾有「自测」；全过 = 你对项目的掌握是所有权级的。司徒接手小程序也可直接共用本手册。
> **时效**：结构按 2026-09-04 实测核对（routers 12 个 / 数据表 23 张 / web 页面 7 个）。以后结构变了，先改这份手册。
> **原则**：你不需要记住所有答案，但必须握住「验证答案」的钥匙。

## 第 0 讲 · 开机图：一张图看懂整个系统

### 0.1 六个框

```
            【用户手机】
      微信小程序  ‖  网页版(PWA)
           ╲        ╱
            ╲      ╱   HTTPS（带 JWT「手环」）
        ┌─────────────────────┐
        │  Azure Web App      │  ← 后端 FastAPI 单体
        │  hkmu-campus-sea    │     (你的全部业务逻辑)
        └──┬───────┬───────┬──┘
           │       │       │
   ┌───────▼──┐ ┌──▼────┐ ┌▼─────────────┐
   │ Supabase │ │Supabase│ │ 微信开放平台   │
   │ Postgres │ │Storage │ │ ·内容审核API   │
   │ (数据库)  │ │ (头像等)│ │ ·登录(openid) │
   └──────────┘ └───────┘ └──────────────┘

   旁边两个后勤：GitHub(代码+CI 自动测试) · ACR(镜像仓库=打包好的后端)
```

用餐厅打比方：**小程序/网页是店面**（顾客看得见摸得着）；**Azure 后端是厨房**（接单、做菜、管账）；**Supabase 是仓库**（所有食材和账本）；**微信开放平台是外部供应商**（安检和身份核验）。

### 0.2 如果某个框挂了，世界会怎样（理解每个框的最快方式）

| 框 | 挂了的样子 | 历史上发生过吗 |
|---|-----------|--------------|
| Azure Web App | 全站 503/无响应，两端一起死 | ✅ 2026-07-07 订阅额度用完，403 全挂 3 小时 |
| Supabase Postgres | 能打开但所有数据加载失败（帖子/课表全空） | ✅ 免费版会自动休眠（pause），有恢复 runbook |
| 微信审核 API | 发帖/改资料被拦下（fail-closed 设计：审核服务不通就不放行） | ✅ 2026-05~08 审核 503 三个月（真凶是 URL 写错） |
| 小程序端 | 网页版正常，小程序白屏/打不开 | ✅ wxml 编译错曾让所有真机打不开 |
| GitHub/CI | 用户无感，只是新改动发不上去 | — |

### 0.3 一次请求的完整旅行（以「发帖」为例，背下来）

1. 用户在小程序写好帖子点发布 →
2. 小程序发 `POST https://hkmu-campus-sea.azurewebsites.net/api/v1/posts`，**请求头里带上 JWT**（登录时领的「手环」，证明「我是谁」）→
3. 后端先验手环（JWT 解码+查库确认用户有效）→
4. 正文过**安检门**：调微信 imgSecCheck，不通过直接拒绝 →
5. **原文存进 `posts` 表**（后端不转义——存的就是用户打的字）→
6. 前端拿到数据渲染时才转义（`{{}}` / `textContent` 自动防 XSS）→ 别人刷到这条帖子。

> 记住这个不对称：**安检在入口（后端），防毒在出口（前端渲染）**。这是全项目最重要的安全设计，改任何涉及用户文本的功能都不能破坏它。

## 第 1 讲 · 后端：一个 FastAPI 单体（`backend/app/`）

「单体」= 所有功能在**一个程序**里，没有微服务。好处：简单、一处部署；代价：改任何功能都在同一个仓库里动刀。

### 1.1 路由层 `routers/`（12 个文件 = 12 类功能，URL 前缀都是 `/api/v1`）

| 文件 | 管什么 | 代表端点 |
|------|--------|---------|
| `auth.py` | 注册/登录/登出/微信 openid 登录 | `POST /auth/login` |
| `posts.py` | 帖子 CRUD、点赞、评论、评论回复+图片 | `GET /posts` |
| `courses.py` | 选课系统全部（最大文件，1500+ 行） | `GET /courses/graduation-status` |
| `users.py` | 个人资料、好友、entry_level | `PUT /users/me` |
| `news.py` | 校园新闻+新闻评论 | `GET /news` |
| `lostfound.py` | 失物招领 | `GET /lostfound` |
| `messages.py` | 私信（REST + WebSocket 双通道） | `GET /messages/history` |
| `push.py` | 订阅消息/推送订阅 | — |
| `upload.py` | 图片上传（转存 Supabase Storage） | `POST /upload/image` |
| `reports.py` | 举报入口（帖/评/失物/用户） | `POST /reports` |
| `feedback.py` | 用户反馈表单 | `POST /feedback` |
| `log.py` | 前端错误上报（小程序原生错误监控） | `POST /log` |

### 1.2 服务层 `services/`（9 个，路由背后的「专业部门」）

| 文件 | 干什么（一句人话） |
|------|------------------|
| `auth_service.py` | 发手环/验手环的总调度 |
| `content_security.py` | 安检门：调微信 imgSecCheck，全场景统一走它 |
| `wechat_service.py` | 和微信服务器打交道（登录 code 换 openid、拿审核 token） |
| `storage_service.py` | 图片文件存取 Supabase Storage |
| `websocket_manager.py` | 私信实时推送的「接线员」（WS 断了就降级轮询） |
| `push_service.py` | 订阅消息推送 |
| `email_service.py` | 邮件验证码 |
| `rate_limiter.py` | 限流：防止有人狂刷接口 |
| `cache.py` | 热数据缓存（课程目录、信息流，减数据库压力） |

### 1.3 数据字典 `data/`（6 个文件，全是选课系统的「官方规则」）

`programmes.py / programme_rules.py / programme_rules_extra.py / programme_year_map.py / ge_courses.py / ge_catalog_enrichment.py`

它们是**写死在代码里的知识**：55 个专业的毕业要求、年级课表映射、GE 目录。特点：**改它们 = 改代码 = 要走完整发布流程**，不是改数据库。

### 1.4 认证体系（必考题）

1. 用户首次登录（网页账密 或 小程序微信授权）→
2. 微信端：小程序拿 code → 后端找微信换 **openid**（用户在微信世界的身份证号）→
3. 后端发 **JWT**（一枚带签名的「手环」，里面有 user_id 和过期时间，默认短期）→
4. 同时存一枚长期 **refresh_token** 进 `refresh_tokens` 表（手环过期了拿它换新，不用重新登录）→
5. 之后每个请求：请求头 `Authorization: Bearer xxx` 带手环，后端验签+查库。

密码存储用 **bcrypt**：单向搅碎，数据库被偷也还原不出明文。
JWT 的意义：后端不用记「谁在线」，每次验手环即可——这让后端可以随便重启，不丢登录态。

### 1.5 中间件（`main.py` 里挂的三道全局工序）

- **CORS**：允许网页/小程序跨域调后端
- **GZip**：响应压缩，省流量提速度
- **OpenTelemetry**：性能遥测（AppRequests 指标，Azure 门户可看）

## 第 2 讲 · 数据：Supabase（PostgreSQL）的 23 张表

数据库在 Supabase（免费版，AWS 日本机房）。表分四组记：

### 2.1 身份组（5 张）
`users`（核心：账号、昵称、头像、openid、entry_term、entry_level）、`refresh_tokens`（换新手的凭证）、`email_tokens`（邮箱验证码）、`push_subscriptions`（推送订阅）、`friendships`（好友关系）

### 2.2 内容组（8 张）
`posts` / `post_likes` / `comments`（评论+两层回复）/ `news` / `news_comments` / `lostfound` / `reports`（举报）/ `feedback`

### 2.3 选课组（7 张）⚠️ 最特殊
| 表 | 装什么 |
|---|--------|
| `courses` | 1136 门课。⚠️ **`id` 是 TEXT 不是数字 = 课码本身**（如 `DRAM1000ECF`）——写代码按数字查会翻车 |
| `user_courses` | 每个学生的修读记录（进度） |
| `user_course_schedule` | 四年规划排期 |
| `course_reviews` / `course_review_tags` | 课评+标签 |
| `programmes_catalogue` / `course_catalogue` | 全校 98 专业/4675 门的**只读官方目录**（公开 PDF 灌进来的） |

### 2.4 沟通组（3 张）
`messages`（私信正文）、加身份组里与私信搭配的好友表

### 2.5 全项目最关键的一个概念：**「规则在代码，课程在库里」双轨制**

- 「BUS 专业 Year 1 要修哪些课」这类**毕业规则** → 在 `data/programme_rules*.py`（代码）
- 「DRAM1000ECF 这门课存不存在、几学分」这类**课程事实** → 在 `courses` 表（数据库）
- 所以新增 2 门课（如批次 5 的 DRAM 中文班）要**单独灌库**——**代码合了 ≠ 数据有了**。2026-09-04 复盘时我们就被这个 distinction 的记忆偏差坑过一次，最后靠生产探针（`curl /api/v1/courses/DRAM1000ECF`）验明。

## 第 3 讲 · 前端：一套后端，两张脸

### 3.1 网页版 `frontend/`（SPA + PWA）
- **SPA**：只有一个 `index.html` 壳，所有「页面」是 JS 动态画出来的
- **路由**：hash 型——网址是 `.../#/community`、`#/planner`，`#` 后面的词决定显示哪页
- **7 个页面** `js/pages/`：`home / community / planner / news / lostfound / messages / profile`
- **i18n**：三语言（`js/utils/i18n.js`，`data-i18n` 标签系统）
- **PWA**：manifest + Service Worker，可「添加到主屏幕」像 App 一样用。⚠️ SW 会缓存旧页面——改版后看不到新 UI 时，先注销 SW 再怀疑代码（历史踩坑）

### 3.2 微信小程序 `miniprogram/`
- 标准微信结构：`pages/`（页面）、`components/`（组件）、`custom-tab-bar/`（底部导航）、`utils/`、`app.js/json/wxss`
- 和网页版**共用同一个后端**，仅界面技术不同（wxml/wxss 而非 HTML/CSS）
- ⚠️ 所以一个功能经常要**改两端**：PR 里同时出现 `frontend/` 和 `miniprogram/` 的改动是常态，不是重复劳动
- 已知坑：wxml 里 `wx:else` 和 `wx:for` 不能同标签（编译错导致真机全挂过）；websocket 兼容性差 → 私信已降级为轮询方案

**自测**：①网页版网址 `#/planner` 的 `#` 是什么意思？②为什么一个功能常要改两端？③改版后网页行为没变，先查什么？

## 第 4 讲 · 发布：三条独立的链（最容易误解的一讲）

**核心认知：上生产不是一个动作，是三条互不相干的链。** 历史上所有「我以为发了」事故都源于把它们混为一谈。

### 4.1 后端链（Azure）
```
git 分支 → PR → CI 自动跑 pytest(220+ 用例) → 合 main
→ 本地 docker buildx(amd64 镜像) → 推到 ACR
→ az webapp config/container 更新 → 重启 → curl /api/health 验证
```
- 完整配方已固化在 **`deploy-azure` skill** 里（含 VPN/凭证/灌库所有坑），部署时让 Claude 走它，不要手工凭记忆敲
- 镜像 tag = commit 短 hash（如 `41bde1b`），**可回滚 = 换回上一个 tag 重启**

### 4.2 小程序链（微信）
```
微信开发者工具 打开 miniprogram/ → 点「上传」→ 版本号+备注
→ 微信公众平台 提交审核 → 审核通过 → 发布
```
- **与 Azure 完全无关**——后端更新一万次，小程序不传就永远是旧版
- 这就是「小程序待上传」成为**挂账之王**的原因：它无法自动、必须有人开工具点鼠标
- 挂账现状（2026-09-04）：用户协议/举报扩展/评论升级等**多版未传**

### 4.3 数据链（灌库）
新课程/规则数据 → `scripts/seed_courses.py` 直连，或 **REST upsert**（本地 VPN 挡 Supabase 时走 443）
→ **代码合了 ≠ 数据有了**（见 2.5）

### 4.4 「一个改动到用户手上」检查单
| 改动类型 | 必须做的 |
|---------|---------|
| 纯后端逻辑 | 走 4.1 |
| 涉及新课程/规则数据 | 4.1 + 4.3 |
| 网页前端 | 随 4.1（静态文件由后端同仓服务） |
| 小程序界面 | **4.2（手动！）** |
| 数据库表结构（DDL） | 4.1 + 注意：新容器启动时 `init_db` 自动加列——但**DDL 注释里绝不能有分号**（历史启动崩溃真凶） |

**自测**：①三条链各一句话；②「评论回复功能上线」要过哪几条链？③为什么小程序更新总是滞后？

## 第 5 讲 · 运维：自查五连、应急三招、事故档案、钥匙清单

### 5.1 生产自查五连（10 分钟内，任何人都能做）

```bash
# ① 活着吗
curl -s https://hkmu-campus-sea.azurewebsites.net/api/health
# ② 数据对吗（课程探针：任选一个真实课码）
curl -s https://hkmu-campus-sea.azurewebsites.net/api/v1/courses/DRAM1000ECF
```
③ **日志**：Azure 门户 → hkmu-campus-sea → Log stream（看实时报错；后端日志里 grep `stable_token`/`ERROR`）
④ **小程序数据**：微信公众平台 → 数据分析（日活/新增/来源）
⑤ **前端错误**：小程序后台错误日志（`log.py` 收的上报）

### 5.2 应急三招
1. **看日志定位**（先日志后猜测——503 三个月误诊的教训）
2. **重启**：Azure 门户 → Web App → Restart（解决大部分「莫名其妙」）
3. **回滚**：把容器镜像换回上一个 tag（= commit hash）再重启

### 5.3 事故档案（三大案，症状→真因→下次第一步）

| 事故 | 症状 | 真因 | 再遇到，第一步 |
|------|------|------|--------------|
| 2026-07-07 全站 403 | 所有请求 403 | Azure 免费额度耗尽→订阅被禁 | 查订阅状态，不是查代码 |
| 审核 503 三个月 | 发帖被拦/审核接口 503 | `_TOKEN_URL` 写错（404），不是 IP 白名单 | 后端日志搜 stable_token，先排除最蠢的原因 |
| Supabase pause | 数据全空/连接失败 | 免费版一周无流量自动休眠 | 跑恢复 runbook（memory: supabase-pause-recovery），keepalive 在防 |

### 5.4 钥匙清单（谁能动什么，凭证在哪）

| 系统 | 用途 | 凭证位置 |
|------|------|---------|
| Azure | 生产服务器 | Azure 账号登录（订阅=PAYG） |
| Supabase | 数据库+存储 | Dashboard 登录；连接串在 Azure 应用配置（appsettings），不在代码里 |
| ACR 镜像仓库 | 存后端镜像 | admin 凭证（memory/部署 skill 有） |
| 微信小程序后台 | 发布/数据/审核 | 你个人微信扫码 |
| GitHub | 代码+CI | 账号登录；**main 有分支保护，必须走 PR** |

⚠️ 本手册刻意**不含任何密钥明文**。钥匙认「在哪」，不认「是什么」——需要值时去对应系统现取。

## 附录 A · 术语表（人话版）

| 术语 | 人话 |
|------|------|
| JWT | 加了签名的电子手环，证明「我是谁」，过期作废 |
| openid | 用户在微信世界的永久身份证号（每个小程序不同） |
| bcrypt | 单向搅碎机：密码进去出碎渣，碎渣对得上但还原不回去 |
| API/端点 | 后端开的一个「服务窗口」，如 `/api/v1/posts` |
| PR | 拉别人来看你的改动，看完合并进 main |
| CI | 每次提 PR 机器人自动跑 220+ 测试，绿灯才准合 |
| 镜像 | 把后端程序+依赖打包成的一整台「现成机器」 |
| ACR | 存这些机器的仓库（Azure 家的） |
| seed/灌库 | 把数据种子写进生产数据库的动作 |
| DDL | 建表/改表结构的 SQL |
| SPA | 单页应用：网页其实只有一页，内容 JS 现画 |
| SW (Service Worker) | 浏览器里的管家，缓存页面让网页能离线/像 App |
| WebSocket | 服务器能主动推消息的常开电话线（私信用） |
| 轮询 | 电话线不通时改成的「每 3 秒问一次有没有新消息」 |
| imgSecCheck | 微信官方内容安检 API，涉文字全场景必过 |
| fail-closed | 安检服务不通就一律拦下（宁可误拦不可放行） |
