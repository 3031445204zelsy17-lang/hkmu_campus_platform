## 1. 旧方案结论回顾(2026-07-31,仍然有效)

- 🥇 **技术栈:RN + Expo**——JS 逻辑复用 70-80%、EAS 云构建免 Mac、Android 同码、Apple 审核无歧视。
- ❌ Capacitor(4.2 套壳墙)、SwiftUI(0 复用无 Android)、Flutter(Dart 不复用)。
- 当时挂起的两个待定项:**① 栈** ② 上架范围**——本文档收口第 ② 项。
- ⚠️ **修正旧评估一处失真(2026-09-07 核实)**:旧文称"supabase-js 最成熟(和网页同 SDK)"——实际网页/小程序从来都走 **FastAPI REST 后端代理上传**,客户端零 Supabase 直连(证据见 §9.1)。iOS 同样零直连,复用面=FastAPI REST,结论不变、依据更准。

## 6. 稳定度评估

| 层面 | A/B 外区路线 | C 国区路线 |
|---|---|---|
| **架构** | 单后端 = 现有 prod 稳定体系(已跑正式版小程序流量,镜像部署/CI/告警全成熟);App 只是新增客户端,后端风险增量小 | 双部署 = 双倍故障面:两套部署/监控/告警,数据一致性边界(内地生数据不出境),Supabase 海外+境内 DB 双轨维护 |
| **审核波动** | 首审 2-7 天,长尾 3-4 周(4.3 Spam 为最大变数);过审后更新审核 1-2 天,节奏可控 | 同左 + 备案流程 30-40 天 + Apple 侧对国区 App 的备案一致性复查;微信侧已示范过"运营期复查/被举报下架"模式 |
| **运营/政策** | Apple 政策全球稳定;UGC 五件套补齐后可持续,风险集中在内容治理本身 | 工信部政策变动敏感;备案周年/复查;数据跨境红线不可试探 |
| **依赖第三方** | EAS 免费额度 15 builds/月(超了 $19/月,量级无虞);Supabase/Azure 现有依赖不变 | + 境内云商(备案绑定)、内容安全厂商(境内版) |

**结论:外区路线稳定度 = 现有体系 + 审核一次性波动;国区路线 = 结构性双倍运维 + 政策敞口。**

### 7.1 vibe 模式修正(纯 AI 主写,人只拆任务+验收)

按团队 vibe-coding SOP(CC 主写 + 人审),瓶颈从"写码速度"变为"验收带宽 + 外部时钟",周期压缩 ~2.5-3 倍:

| 阶段 | 常规(15-20h/周) | vibe·现实档(每天 2-4h 验收) | vibe·全职档(每天 6-8h) |
|---|---|---|---|
| 0 假设验证 | ~1 周 | 1-2 天(拉数据 AI 干,访谈仍需本人) | 1 天 |
| 1 后端合规 | 1-1.5 周 | 1-2 天(现成模式套用,pytest 门禁兜底) | 1 天 |
| 2 RN 骨架+登录+核心三件套 | 2-3 周 | 3-4 天 | 2 天 |
| 3 全量页面+推送(planner 大头) | 2-3 周 | 4-6 天 | 3-4 天 |
| 4 TestFlight 内测修反馈 | 1 周+ | 2-3 天(装机/走查是人工节奏) | 2 天 |
| 5 材料+首审 | 0.5-3 周 | 半天 + 审核 2-7 天(外部时钟) | 同左 |
| **合计 0→TestFlight** | ~5-8 周 | **~2-3 周** | **~1.5-2 周** |
| **合计 0→外区过审** | ~6-10 周 | **~3-4.5 周** | **~2.5-3 周** |

**vibe 模式四个真实瓶颈(周期表压不掉)**:
1. **验收带宽 = 人的时间**。AI 一天能吐完全部 16 页,但审不过来;"一个 prompt 一件事 + 人审"的 SOP 本身按人的带宽设计,全职档与现实档差距几乎全在每天可投入小时数。
2. **RN 是新栈,但坑由 AI 扛**。对 vibe 友好(人不用先学 RN);代价是排坑来回吃时间,尤其 expo-notifications 首次接 EAS 构建。
3. **planner 是唯一 vibe 加速有限的件**。页面可一天吐完,但 107 专业级联 + 三语搜索折叠 + 学分池的交互调优(动画/边界/简繁)仍靠真机走查迭代,按 4-6 天估,别指望 1 天。
4. **测试自动化决定上限**。RN 侧等价于 miniprogram-automator 的配方 = Expo web 预览快速走查(秒级热更新)+ Codex build-ios-apps 模拟器视觉验证;不搭,真机来回会吃掉省下的时间。

⇒ **纯 vibe 全职:0→外区过审 ~3 周封顶(其中 Apple 审核 2-7 天);现实档(课业之余):~3-4.5 周。后端 FR1c 无论 iOS 做不做都值得先做(现存风险,零依赖)。**

## 9. 红档核实结果(2026-09-07,4 路子代理 + 3 轮检索,全 file:line/一手来源)

### 9.1 图片上传链路 → iOS 零改造 ✅(高置信,全量 grep 证据)

- **全部资产(帖子/评论/失物/头像)统一走 `POST /api/v1/upload?module=<m>` multipart + Bearer token**,后端代理上传 Supabase Storage(桶 `uploads`,多尺寸变体+canonical URL);web 头像另有专用 `POST /users/me/avatar`(同为代理)。**两个客户端零 Supabase SDK、零签名 URL、零 anon/service key 暴露**;service key 仅存 `backend/.env`(gitignored)与 Azure 配置。
- iOS 端照抄该链(FormData + fetch + Authorization),**无任何新增后端接口、无凭据下发**。
- 附带确认:cacheControl 修复已落地(multipart 字段 + 1 年 immutable + 头像内容哈希版本化路径)。
- ⚠️ 顺带发现两个小缺口(不阻塞 iOS,🟠 择机修):① `create_post` 与失物 `create_item` 接受任意 `image_url` 不做桶校验(评论创建反而有 `is_module_image_url`——不对称);② `users.py` 旧注释还描述前代头像路径方案。

### 9.2 登录与 Sign in with Apple → 后端小改、零 DB 迁移 ✅

- 现有四法:用户名+密码(legacy)/ 邮箱+密码(完整验证链)/ **Google(web 端到端真实可用**,GIS SDK,受 `GOOGLE_CLIENT_ID` 门控)/ 微信小程序(code2session)。
- **Apple 接入改造量小**:`POST /auth/apple` 照抄 Google handler 三步匹配模板;新增 `apple_service.py` 自写 JWKS/RS256 验签(python-jose 已在依赖,无现成 helper);users 表通用 `oauth_provider`+`oauth_id` 落位(`='apple'` + token `sub`),唯一索引已建,**零迁移**;Apple `email_verified` 声明可直接置位。
- ⚠️ **一个待决策的现有设计约束**:一行用户仅一个 OAuth 身份槽,且 Google handler 的邮箱匹配分支会无条件覆盖已有 provider(Apple 复制粘贴会冲掉微信/Google 链接);Apple 私密中继地址(`@privaterelay.appleid.com`)使邮箱匹配常不触发。建议:接受"单 OAuth 身份 + 邮箱做 join"(小改+防覆盖守卫),暂不拆独立身份表。
- 4.8 落地即二选一:**iOS 保留 Google 登录 ⇒ 必须同时上 Apple**(邮箱+Google+Apple 三件套)/ 或砍到邮箱单选(零 Apple 改造,但体验降级)。
- 附带:现有 OAuth 端点零测试覆盖,新端点必须带 tests(CI 门禁已在)。
