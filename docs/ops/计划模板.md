# 计划模板(2026-09-21 起,新计划文档必用)

> 四层对齐的源头件:需求→计划→代码→系统。本模板保证①②层不出"沉默错误"。
> 复制本文件改名后填写;一节都不能删,没内容就写「无」。

```markdown
# <计划名>-<YYYYMMDD>.md

## 保鲜期与触发器(必填)
- 保鲜期至: YYYY-MM-DD(到期必须重验全文,过保鲜期的计划禁止据此开工)
- 重验触发器: <事件列表,如"转付费时/外部政策变更时/依赖大版本升级时">

## 目标(一句话)
<做什么、为什么、不做什么>

## 前提清单(必填 — 每条开工前用命令验证,抄进 project-start 的开工门禁)
| # | 前提假设 | 验证命令 | 结果 |
|---|---------|---------|------|
| 1 | 例:订阅是学生类型 | python3 scripts/infra_audit.py | ✅/❌ |
| 2 | | | |

> 隐含前提也要挖出来(账号状态/额度/版本/政策/他人在改的东西)。
> 纸面结论(调研/memory/文档)≠系统事实,以命令实测为准。

## 验收标准(必填 — 开工前写完,写完代码才补=作废)
- [ ] <可执行的检查:跑什么、看到什么算过>
- [ ] 例:curl /api/health 返回 {"status":"ok","database":"up"}

## 挑刺记录(必填 — 计划过对抗审查才准开工)
- 挑刺方: Codex(或另一独立视角)  日期: YYYY-MM-DD
- 发现: <编号列出;含对前提/验收的质疑>
- 回应/修订: <逐条:采纳改了什么 / 不采纳为什么>
- 复核: CC 确认修订落回本文件 ✅

## 任务表
| ID | 任务 | 文件 | 验收 | 状态 |
|----|------|------|------|------|
| T1 | | | | ☐ |

## 变更日志
- YYYY-MM-DD 建档
```

## 使用纪律(三条,对应三层失灵)

1. **前提不验不开工**:任务表第一行之前,前提清单每条都要有 ✅(project-start skill 已装门禁)
2. **计划不挑刺不开工**:用 CC 出计划 → Codex 挑刺 → CC 复核落回(即全局 CLAUDE.md 的双工具协作,从"重大选型才用"升级为"所有计划必用";纯代码小改可豁免,由用户判断)
3. **过期计划禁止开工**:超过保鲜期或踩中触发器 → 先重验前提再动

> 基建类计划另加一条:动云前跑 `python3 scripts/infra_audit.py` 点货,动完再跑一次,前后对账。
